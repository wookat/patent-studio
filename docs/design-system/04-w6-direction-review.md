### 0.2 一句话定位

| 方向 | 一句话 | 一眼像谁 |
|---|---|---|
| **A** Overleaf 进化版 | 保留 Overleaf 的"左 rail + 文件树 + 源码 / PDF"骨架，把顶栏调浅、把 AI / 审阅 / 历史改成右侧**伴随栏**，用飞书的内容优先和 Notion 的留白圆角做"推陈出新" | 浅色 Overleaf |
| **B** 文档产品式极简 | 白壳暖灰、28px 大标题、几乎无边框，靠留白分层；工作台默认两栏，功能全部收进右侧抽屉 | 飞书文档 / Notion |
| **C** 专业工具式高密度 | 冷灰 hairline、13px 基准、状态色点 + 语义色、深色一等公民；默认两栏，≥1680 可开三栏 | Linear / VS Code |

### 0.3 推荐与理由（实事求是）

**推荐 A（`a-overleaf-plus`）为主壳，合并 C 的密度原语与移动壳、B 的字阶与登录 / 客户页。**

1. 老板原话是"参考 Overleaf 并推陈出新"。四方并排里只有 A 一眼仍是 Overleaf 家族（左 rail、文件树、源码 | PDF 双栏、绿色"构建"锚点），同时肉眼可辨地变了：顶栏浅色、面层分离、伴随栏、H1 24 [实测]。B、C 都是"另起一套"，Overleaf 血缘只剩"源码 | PDF"这一件事。
2. **三方向在解决波次 5 主要问题上是同等有效的**——这点必须说清楚，不存在"只有一条能救"。探针：工作台首屏可见控件 W5 **91** → A 41 / B 31 / C 32；移动编辑 < 44px 控件 W5 **19/23** → A 5/11、B 7/12、C **0/15**；首页高度档 W5 10 档 → 三者均 6 档；阴影变体 W5 全站 1 种 → A 1–6 / B 2–7 / C 3–8 种 [实测]。所以选择标准不是"谁修了 bug"，而是"谁最符合老板的定位 + 落地最便宜 + 代理师效率不掉"。
3. **A 落地最便宜**：波次 5 的 token（OKLCH 冷灰 10 阶、绿主色、28/32/36 控件档）本来就是从 Overleaf 抄来的，A 的 token 表与之"基本等值"，改动集中在新增 4 层面 + 伴随栏 + 页面版式 [方向自述 §9.2，与 W5 `index.css` 对照后我认同]；B 要整体换暖灰并重校 recharts 色，C 要把灰阶从 10 阶扩到 12 阶并重写深色。
4. **A 的短板明确且可借补**：视觉新鲜感最弱（3/5）、移动端 375 仍有 5 个 < 44 的控件、台账缺状态色点 / 期限热度。这三点 C 都做到了极致（移动 0 个 < 44、`StatusDot` / `Heat` / `Countdown` 原语、四层深色），B 的 28px 标题与登录 / 客户页的"产品感"也可直接搬进 A 的版式，不冲突。
5. **如果老板更看重"代理师每天 8 小时的效率"而非 Overleaf 血缘，C 是更好的答案**（专业效率唯一 5 分，移动可用性唯一 5 分）；C 的代价是初见门槛（10–11px 辅助文字大量出现 [实测]）、与 benchmark 有 4 处有意偏离、深色 token 维护量翻倍。B 不建议作为主方向：它最"好看"、最亲和，但对台账 / 三视图这类高密度页面牺牲了每屏 2 行 [方向自述]，而且"一屏一 primary"的纪律要靠 shell 层逻辑维持，工程成本最高。

**总分**（7 维各 1–5，见 §1）：A **28** / C **28** / B **24**。A 与 C 同分——分差在"契合度 + 落地成本"（A 胜）与"专业效率 + 移动端"（C 胜）之间，这正是老板要做的取舍；我按老板原话押 A。

## 2. 三视角质疑（各 ≥ 5 条）

### 2.1 技术负责人（落地 / 架构）

1. **A 的"伴随栏"不是 CSS 改动**：W5 用 dockview 把 AI / 审阅 / 历史作为 Tab 面板，改成右侧固定 360 伴随栏需要重新设计面板编排与视图 store，三方向都要做这件事（A 伴随栏 / B 抽屉 / C 抽屉），成本在 shell 层而非 token 层——三份文档都低估了 hash 路由要承载抽屉 / 伴随状态这件事 [推断]。
2. **B 的暖灰不能"等值搬家"**：`--n0..n9` 全换值意味着所有直接引用 `--n*` 的 className 都要目检，recharts 色板重校，`#/__ds` 也要重做；B 作者自陈"中偏大"是实话，我认为偏大。
3. **C 的 12 阶灰 + 语义色 dot 变体 + 深色独立层**是最多的 token 维护量；如果后续再来一轮方向调整，C 的 token 面最大、回滚最贵。
4. **三方向的圆角 / 字号 / 高度档互不兼容**（A 5 档圆角、B/C 3 档；C 顶栏控件 28 vs benchmark 32），合并时必须先定一套档，否则 `components/ui` 会出现三套尺寸变体。
5. **三份原型都是静态 HTML**，没有 CodeMirror / ProseMirror / react-pdf / dockview 的真实约束：源码区行高、PDF.js 画布在深色下的观感、dockview 面板头样式覆盖，都可能让实际效果打折 [推断]；A 与 W5 最接近，这一风险最小。
6. **纸面恒白**：三方向深色下纸面都保持白（`workbench--1440-dark` 三张均可见）[实测]，但 B 的 `#111` 画布与白纸亮度差最大，作者自陈；C 的四层深色最稳。
7. `h1` 语义：C 首页 / 工作台探针 `h1: []`，标题用了非 h1 元素 [实测]，落地时须改回语义标签（读屏 / 大纲）。

### 2.2 UX 研究员（可用性 / 认知负荷）

1. **B 最好看但最"读不出层级"**：`strip-home.png` 里 B 的表格边界靠留白，投影 / 低对比屏上行与行难分，作者自己也标了 [方向自述]；专业台账不能靠"读"来分层。
2. **C 的 10px 辅助文字**在首页 / 工作台 / 客户页 / AI 面板均出现 [实测]，对 40+ 岁代理师与客户是真实门槛；"客户页放大到 14–15" 只覆盖了 S9。
3. **A 移动端仍有 5 个 < 44 控件**（顶栏 40、段控件 34）[实测]，没有达到 L15 的"全部 ≥ 44"；三者只有 C 做到 0。
4. **三方向的移动"更多" Sheet 与底部 Tab 方案不同**（A 浮动构建胶囊、B 纸面浮条、C Markdown 快捷键盘）[实测]，合并时要做一次任务流对比，不能三取其一拍脑袋。
5. **状态语义**：A / B 用 pill 文字，C 用色点 + 文字；代理师扫 50 行台账时色点更快 [推断]，但色弱用户必须有文字，C 已强制并列，A/B 需补点。
6. **一屏一 primary**（benchmark C3）：A 工作台默认屏只有"构建"一个 primary [实测]；B 靠抽屉内不放 primary 的纪律；C 状态栏 + 顶栏两处都有绿色实底按钮 [实测 `strip-workbench.png`]，落地时要收敛。
7. **首页 KPI 卡**：W5 三卡为 0 被 audit #9 点名；A 保留 3 卡但给了非零过滤与右栏 [实测]；B 改成摘要行；C 保留 4 卡 + 分组栏。哪种最省认知需要用真实机构数据验证，原型数据都是"填满的" [推断]。

### 2.3 资深专利代理师 / 领域专家（业务契合）

1. **期限是代理师的命**：三方向首页都有期限区块，但只有 C 把"热度 / 倒计时"做成列级原语进入台账行 [实测]；A 的期限在右栏卡片、B 在行内 chip，都需要多看一眼。
2. **OA 答复流程没有出现在任何一套首页**（W5 也没有）：三方向都以"案卷"为中心，缺"今日答复 / 待客户确认 / 待递交"这类**工作队列**视图，这是 W6 之后必须补的 IA，不是视觉问题。
3. **三视图（源码 / 版面 / PDF）在 1440 下**：A、B 以两栏 + 浮层做，C 也默认两栏（三栏 ≥1680）[实测 `w6-review/compare/tv3.jpg`]；代理师核对权利要求与说明书对应关系时确实要三栏，1440 显示器仍是机构主流 [推断]，三方向都没解决，只有 C 明确了阈值。
4. **CriticMarkup 审阅**：三方向都在右侧承载审阅列表 [实测]，但只有 A 的原型把"定位到源码 / 版面"动作做在批注卡片上 [实测 `w6-review/compare/tv3.jpg` 左]；C 的批注在纸面用 `span.cm` 高 36 承载，作者承认移动端命不中 [方向自述 §9]。
5. **客户审阅页**：W5 最素（audit #15）；三方向都补了机构头 + 动作条 [实测 `w6-review/compare/client3.jpg`]；B 最有"发给客户不丢人"的品牌感，C 最像内部工具——客户页应借 B。
6. **递交页**：三方向都做了 H1 + 清单 + 步骤 [实测]；但都没有"CNIPA XML 校验结果 / 附图 EMF 校验"的显式区块——这是递交前真实卡点，需在 W7 内容层补，不影响视觉方向选择。
7. **深色模式**：代理师加班盯 PDF，深色壳 + 白纸是刚需；A 蓝灰 5 层 [实测] 与 Overleaf 现有深色习惯最接近，切换成本最低。

## 4. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| A 的"新鲜感"仍不够，老板再次觉得"跟没改差不多" | 返工一轮 | 先落 §3 中 #1 / #3 / #6 / #9 四项（状态点、深色四层、H1 28、KPI 摘要行）——这四项是 A/B/C 并排时最先被眼睛捕捉的差异；用 `strip-*.png` 同口径复截验证 |
| 伴随栏改造触及 dockview 面板编排与 hash 路由状态 | shell 工期超估 | 先在 `#/__ds` 或独立 storybook 页做伴随栏容器 + 空面板，跑通"打开 / 关闭 / 宽度 / 与 dockview 共存"再接业务面板；不动 CodeMirror / ProseMirror / react-pdf 内核 |
| 三方向原语尺寸档不兼容，合并时长出三套变体 | 统一性下降 | 合并前先冻结一张"尺寸档 / 圆角档 / 字阶"总表（以 A 为底，字阶取 B，最小 11px），所有借入项先对表再进 `components/ui` |
| 静态原型 vs 真实内核（CodeMirror 行高、PDF.js 深色画布、dockview 头样式） | 实际观感打折 | 第一个落地会话就在真实 `#/p/method` 上做，而不是继续做 HTML；每屏用 `shot.js` 同口径复截 |
| 移动端只按 CSS 高度判定 ≥ 44，未真机触控；axe 未跑 | 可访问性回归 | 落地后跑 axe-core + 真机 iOS / Android 各一台；`prefers-reduced-motion` 在 CSS 层已写，需真机确认 |
| 借入 C 的状态色点依赖色觉 | 色弱用户 | 硬性"点 + 文字并列"，并在 `#/__ds` 加色弱模拟截图 |
| 老板可能更偏好 C 的效率或 B 的观感 | 方向选错 | 本文 §0.3-5 已给出"若更看重效率选 C"的替代结论；三方向对 W5 问题的修复力相当，切换主壳的沉没成本主要在 token（A 最小） |
| 工作队列（OA / 待确认 / 待递交）IA 缺失（三方向与 W5 皆无） | 业务契合不足 | 列入 W7 内容层，不阻塞视觉方向；在 A 首页右栏预留"今日队列"位 |
