# 迭代修订工作流

用于修改、补充、合并、纠错、加强保护点或承接既有稿。

## 修订分类

- **合并/补充**：新材料、新实施例、新数据、新模块、扩展场景
- **纠错**：事实错误、参数错、公式不一致、先行技术引错、术语问题
- **权项加强**：调整权项书或保护重心，不加新技术事实
- **重写**：用户明确要求从源材料重建或更换发明方向

## 输入

基线稿（案内三书或用户指认版本）+ 修订请求/补充材料。基线缺失且无法推断时先问。

## 密度校准（164 篇授权件基准，详见 references/benchmarks.md）

修订「补强/加厚」类请求时先量后写：

- **p25 以下** = 偏薄必补；**中位** = 合格；**p75** = 丰满。各节中位：背景 ~584 字、发明内容 ~2268、具体实施方式 ~6626、说明书 ~10246、权项 8 项/权1 ~686 字
- **实施方式是最大扩写杠杆**——扩写素材按优先级：参数取值依据（为何选这个值/范围）→ 等效变体段（"在另一些实施例中，也可……"）→ 按图逐步走查（图1 步骤→图2 模块→图3 时序逐一展开）→ 异常/边界处理
- 不越红线：扩写用真实技术细节展开已有内容，不编造实验数据、性能数字、对比表格
- 背景技术补厚用「场景→技术路线逐代演进→缺陷→缺位总结」段落式（枚举式「其一/其二」仅 7% 授权件用）

## 修订规则

- 用户明显在改旧稿就不退回全量挖掘，除非明确要求重来
- 保留未受影响节；只增/改受影响节，然后审计跨节一致性（术语/参数/图号/支持映射）
- 修订动了技术实质 → 评估查新与权项支持是否需刷新
- 默认不覆盖既有交付：平台内经提案（patch/critic/comment）给出，人点应用；git 历史即版本链

## 留档摘要（答复里给，不写进正文）

合并/补充：
```markdown
## 合并摘要（留档）
```
3–6 句中文：改了哪些节、为什么、对权项/查新结论的影响、一致性检查结果。

纠错：
```markdown
## 纠正摘要（留档）
```
2–5 句中文：改了哪里、依据、对权项/查新结论的影响。

权项加强：说明是范围/表述侧重调整（未加新事实时注明）。
